# i18n

- Status: Accepted
- Created: 2026-08-10
- Updated: 2026-08-15 (レビューで初回描画・builtin 関数名・エラー構造化・LegacyBackup の扱いを決定)

## Objective

UI の表示言語を日本語と英語から選択できるようにし、Chrome・Firefox・Safari で同じ実装を使える国際化の仕組みを提供する。

## Background

cocopy の UI 文言は現在すべて英語のリテラルとして、コンポーネントと `src/lib/` に直接埋め込まれている。
国際化の仕組みは存在せず、`_locales/` も持たない。

翻訳対象は `src/` 全体でおよそ 140 件である。

| 領域 | 件数 | 主な内容 |
| --- | --- | --- |
| `src/components/options/` | 約 75-80 | 最大。`LegacyBackup.tsx` 約 28、`Hints.tsx` 約 9 |
| `src/lib/` | 約 25 | エラーメッセージ、builtin 関数名 |
| `src/components/popup/` | 約 6 | 読み込みエラー、aria-label |
| `src/components/common/` | 約 1 | |

このうち今回翻訳するのは UI のリテラルに限る。
`src/lib/` のエラーメッセージはエラーの構造化 (Error Messages 参照) とあわせて後続の変更とし、
`LegacyBackup.tsx` はバナーのみ (Non-Goals 参照)、builtin 関数名は永続化されるデータであり対象としない。
実際の翻訳対象はおよそ 60-70 件となる。

数量に依存して変化する文言は `LegacyBackup.tsx` の 1 件だけで、それも `function(s)` という表記で済ませている。
言語ごとの複数形規則を扱う必要はない。

ユーザーが言語を選択できることが要件であるため、WebExtensions 標準の `i18n` API は単体では要件を満たさない。
`i18n.getMessage()` はロケール引数を持たず、表示言語は拡張のロード時にブラウザ UI 言語で確定する。
拡張から表示言語を変更する API は存在せず、複数ロケールの動作確認はブラウザを `--lang` 付きで再起動して行う。

参照資料:

- [Chrome Extensions: chrome.i18n](https://developer.chrome.com/docs/extensions/reference/api/i18n)
- [MDN: i18n API](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/i18n)
- [MDN: i18n.getMessage()](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/i18n/getMessage)
- [chromium-extensions: How to manually set my locale](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/rD0LLcSsyY8)

## Goals

- 選択できるようにする: 表示言語を日本語・英語・ブラウザ追従から選択できるようにする。
- 追従する: 明示的な選択がない場合はブラウザの言語設定に追従する。
- 検出する: 翻訳の欠落とキーの誤りを `pnpm run typecheck` で検出する。
- 統一する: Chrome・Firefox・Safari で同一のバンドルを使い、ブラウザごとの分岐を持たない。
- 分離する: 翻訳と言語の決定を UI 層に閉じ、`src/lib/` に言語設定への依存を持ち込まない。
- 維持する: popup の起動性能を維持する。カタログの取得を非同期にせず、言語設定の読み取りを初回描画のブロッカーにしない。

## Non-Goals

- 日本語・英語以外の言語は追加しない。3 言語目以降が必要になった時点で Alternatives Considered を再評価する。
- 言語ごとの複数形規則は扱わない。該当する文言が 1 件しかないため、その 1 件は数量に依存しない表現へ書き換える。
- 外部の翻訳者へ渡すためのカタログ形式 (PO、XLIFF 等) は導入しない。翻訳はリポジトリ内の TypeScript として管理する。
- `_locales/` は導入しない。manifest の `name` と `description` も含めて使用しない (Alternatives Considered 参照)。
- ユーザー定義関数のコードとその実行結果は翻訳しない。`src/lib/builtin.ts` の既定関数はコード本体だけでなく `name` も、新規関数テンプレート `initialCode` も対象としない。いずれも function-store へ永続化されるユーザーデータであり、保存後の言語切り替えに追従できないためである。
- エラーメッセージは今回翻訳しない。エラーの構造化 (code と値を持たせ UI 層で文言を決める) が前提となるため、後続の変更として切り出す (Error Messages 参照)。`MigrationResult.error` は移行時に保存された英文の文字列であり、遡って翻訳できないため恒久的に対象外とする。
- `LegacyBackup.tsx` のページ本体 (`/legacy`) は翻訳しない。移行完了後に削除する予定のページであり、メインページに表示される `LegacyBackupBanner` のみ翻訳する。翻訳よりも文言自体の削減・統合を優先してよく、バナーの 3 変種 (失敗・一部未移行・完了) を短く整理することも実装時に検討する。
- ストア掲載情報 (説明文、スクリーンショット) は各ストアの管理画面で管理し、拡張のビルド対象としない。

## Scenarios

### 表示言語を切り替える

1. ユーザーが options の Settings で言語を選択する。
2. `ConfigStore.update({language})` が `storage.sync` の `cocopy:config` を更新する。
3. `ConfigStore.subscribe` が options と popup の双方へ変更を通知する。
4. `I18nProvider` が新しい言語のカタログを Context へ流し、UI が再描画される。

言語はブラウザアカウント間で同期する。`storage.sync` を使う既存の Config に相乗りするためである。

### 起動時に言語が決まる

1. `I18nProvider` は `detectLanguage()` の結果で即座に描画する。`storage.sync` の読み取りを待たない。
2. `ConfigProvider` の `ConfigStore.read()` が解決し、`language` が `auto` 以外であればそのカタログへ差し替えて再描画する。未設定・`auto` であれば手順 1 の結果を維持する。
3. 以降は `ConfigStore.subscribe` で変更へ追従する。

config の読み取りは `ConfigProvider` (`src/components/common/ConfigContext.tsx`) に集約する。
`I18nProvider` は `useConfig()` から言語を導出するだけで、自前の読み取りを持たない。
popup は `closeAfterCopy` のために元々 config を 1 回読んでおり、その読み取りを共有するため、i18n が popup 起動に読み取りを追加しない。

明示的な言語設定がブラウザ言語と異なる場合に限り、初回描画が一瞬別の言語になる。
popup で翻訳されるのはエラー文言と aria-label 程度であり、通常の起動で目に見える差は生じない。
描画を `read()` の解決まで保留する案は採らない。現状即座に描画している `PopupHeader` まで `storage.sync` を待つことになり、起動性能の維持 (Goals) と矛盾するためである。
解決済み言語を `localStorage` へキャッシュする案も採らない。ちらつきと遅延の両方を避けられるが、`storage.sync` との二重管理という新しい状態を持ち込むためである。

`navigator.language` は Web 標準であり、WebExtensions API に依存しない。

## Architecture

### 構成

```
src/lib/i18n/
  messages.en.ts   英語カタログ (型の定義元)
  messages.ja.ts   日本語カタログ (typeof en に適合)
  detect.ts        navigator.language からの言語判定
  index.ts         Language 型と公開 API

src/components/common/
  I18nContext.tsx  I18nProvider と useT()
```

`src/lib/i18n/` は WebExtensions API を参照しない。純粋な TypeScript として保ち、テストからブラウザ API のモックを不要にする。

### Message Catalog

英語カタログを構造の定義元とし、そこから導出した `Messages` 型 (`typeof en`) へ日本語カタログを適合させる。
キーの追加漏れ、削除漏れ、名前の誤り、文字列と関数の取り違えは `tsc --noEmit` が検出する。

文言そのものの表記と動詞は型では縛れないため、`docs/wordings.md` に基準をまとめる。
カタログにエントリを追加・変更するときはそちらに従う。

```ts
// messages.en.ts
/** A catalog value: a string or a function assembling one. */
type MessageLeaf = string | ((...args: never[]) => string);
type MessageTree = {[key: string]: MessageLeaf | MessageTree};

export const en = {
  settings: {
    title: 'Settings',
    closeAfterCopy: 'Close the popup after copying',
    language: 'Language',
  },
  error: {
    loadFailed: 'Failed to load functions.',
    quotaItem: (bytes: number, limit: number) =>
      `This function is ${bytes} bytes, over the ${limit} byte limit.`,
  },
} satisfies MessageTree;

export type Messages = typeof en;

// messages.ja.ts
import type {Messages} from './messages.en';

export const ja = {
  settings: {
    title: '設定',
    closeAfterCopy: 'コピー後にポップアップを閉じる',
    language: '言語',
  },
  error: {
    loadFailed: '関数の読み込みに失敗しました。',
    quotaItem: (bytes, limit) =>
      `この関数は ${bytes} bytes で、上限の ${limit} bytes を超えています。`,
  },
} satisfies Messages;
```

型付けは `satisfies` で行い、型注釈と `as const` は使わない。

- `as const` を付けると値がリテラル型へ狭まり、`typeof en` へ日本語の値を代入できなくなる。`satisfies` は推論結果を widening したまま検査だけを行うため、この問題がない。
- `en satisfies MessageTree` は「カタログの値は文字列または文字列を返す関数だけ」という不変条件を型で強制する。数値や JSX の混入はここで型エラーになる。
- `ja satisfies Messages` はキーの過不足と値の型 (関数のシグネチャを含む) の不一致を検出する。型注釈 `ja: Messages` と検査能力は同等だが、カタログを一貫して `satisfies` で揃える。

値を持つ文言はテンプレート文字列ではなく関数として定義する。
言語によって値の位置が変わるため、埋め込み位置を各言語のカタログが決定できるようにする。

カタログの値はすべて文字列または文字列を返す関数とし、JSX を含めない (`MessageTree` が型で強制する)。
文中に要素が埋め込まれた文言への方針は Nested Elements を参照する。

### Language Resolution

```ts
export type Language = 'en' | 'ja';
export type LanguageSetting = Language | 'auto';
```

`Config.language` の既定値は `auto` とする。
`auto` は `detect.ts` が `navigator.language` から解決する。

```ts
export function detectLanguage(): Language {
  return navigator.language.startsWith('ja') ? 'ja' : 'en';
}
```

ブラウザ API に触れるのはこの関数だけである。
`i18n.getUILanguage()` は使用しない。WebExtensions API への依存を増やし、`navigator.language` に対する利点がないためである。

### Config Integration

言語設定は `src/lib/config.ts` の `Config` へ追加する。
`Config` は各フィールドが独立して `v.fallback` する前方互換設計を持つため、フィールドの追加は既存バージョンの読み取りを壊さない。

```ts
export interface Config {
  closeAfterCopy: boolean;
  language: LanguageSetting;
}

export const DEFAULT_CONFIG: Config = {
  closeAfterCopy: false,
  language: 'auto',
};
```

`storage.sync` に保存するため、言語設定は端末間で同期する。
不正な値は `v.fallback` により `auto` へ落ちる。

### Distribution

`ConfigContext` と同じ構成で Context を提供する。

```tsx
export function useT(): Messages {
  return useContext(I18nContext) ?? en;
}
```

キー文字列を引数に取る `t('settings.title')` の形式は採らない。
カタログのオブジェクトをそのまま返し、`t.settings.title` として参照する。
補完が効き、存在しないキーが型エラーになる。

Provider の既定値は英語カタログとする。Provider の外側で描画された場合でも文言が欠落しない。

### Error Messages

エラーメッセージの翻訳は本設計の範囲外とし、後続の変更として行う。
当面 `src/lib/` は現状どおり英語の文を投げ、`messageForError()` (`src/components/options/FunctionList.tsx`) と `src/components/popup/Error.tsx` がそのまま表示する。
今回のカタログ導入はこの後続作業と競合しない。

切り出す理由は、構造化の対価が文言によって大きく異なるためである。

- `src/lib/function-store/repository.ts` の throw 28 箇所の大半は `CorruptionError` の診断文であり、ユーザーが行動できる文言は quota・conflict・unsupported-version に限られる。
- `src/lib/eval.ts` の `ParseError`・`ExecutionError` の `message` は JS エンジンまたはユーザーコード由来であり、翻訳対象にならない。sandbox 自身が組み立てる文言は 3 件 (`code is not a function`、戻り値の型エラー、`ReturnsEmpty`) しかない。

後続の変更では、ユーザーが行動可能なエラーを優先して `code` と値を持つ形へ変更し、UI 層が文言を決める。
`src/lib/` は翻訳済みの文字列を持たない。React Context へアクセスできず、sandbox を越える経路も存在するためである。

```ts
// 変更前: repository.ts が文を組み立てる
throw new QuotaError(`Function "${id}" is ${size} bytes, over the ${limit} byte limit.`);

// 変更後: 値だけを持つ
throw new QuotaError({kind: 'item', bytes: size, limit});
```

```ts
// messageForError() が文言を決める
if (error.code === 'quota' && error.detail.kind === 'item') {
  return t.error.quotaItem(error.detail.bytes, error.detail.limit);
}
```

この分離は i18n がなくとも設計として正しく、`messageForError()` は既にその変換点として存在している。

同じ理由で、UI 層の状態にも翻訳済みの文字列を保存しない。
`FunctionsReducer` の `State.error` は「何が起きたか」だけを持つ `ListError` (`{kind: 'operation', error}` または `{kind: 'function-gone'}`) とし、
文言は描画時に `textForListError()` が決める。
dispatch 時に翻訳すると、言語を切り替えても表示済みのエラーが前の言語のまま残る
(reducer は `refresh` で `error` を保持するため、言語変更で消えない)。

`src/lib/eval.ts` の sandbox 発の 3 文言も同様に、種別を popup 側へ渡し `src/components/popup/Error.tsx` が文言へ変換する。
JS エンジンとユーザーコード由来の `message` は原文のまま表示し続ける。

### Nested Elements

文中に JSX 要素が埋め込まれた文言は、要素を文の外へ出して分割する。

対象は `Hints.tsx` の 7 件と `LegacyBackupBanner` の 3 件で、埋め込まれている要素は次のいずれかである。
(`LegacyBackup.tsx` のページ本体は翻訳しない。Non-Goals 参照。)

- API シグネチャ (`render(template, view)`、`throw new Error(...)`)
- 識別子 (`DOMParser`)
- 外部サービス名とリンク (mustache、Function Gallery、sandbox のドキュメント)
- 内部リンク (`Legacy Functions` ページ)

いずれも翻訳対象ではなく、原文のまま残す。
文中の位置も「コード片に続けて説明する」形に揃っているため、分割しても日本語の語順を保てる。

```tsx
<li>
  <code>render(template, view)</code>
  {' — '}
  {t.hints.mustache}
</li>
```

`LegacyBackupBanner` はリンクを文末へ置く。あわせて 3 変種の文言を短く統合することを検討する (Non-Goals 参照)。
このページは移行完了後に削除する予定であり、恒久的な仕組みを合わせる対象としない。

翻訳の中へ JSX を埋め込む仕組みは導入しない。
必要とする文言が存在しないためである。将来必要になった場合は Alternatives Considered の Lingui を再評価する。

### Formatting

日時と数値の書式は選択中の言語に従うことを原則とするが、今回の翻訳対象にはどちらも現れない。

`LegacyBackup.tsx` の `toLocaleDateString()` はロケールを指定せずブラウザの言語に従っているが、ページ本体が翻訳対象外となったため現状のままとする。ページを削除するまでこの食い違いは許容する。

バイト数は `Intl.NumberFormat` を通さず、素の数値とする。
桁区切りの有無で意味が変わらず、対象がエラーメッセージ中の技術的な値に限られるためである (エラーの構造化を後続で行う際も同様)。

### Cross-Browser

翻訳データは JavaScript バンドルの一部となる。
Vite は Chrome・Firefox・Safari へ同一の内容を出力し、manifest の分岐 (MV2/MV3、`web_accessible_resources` の形式、CSP の表現) から独立する。

WebExtensions API への依存は `detectLanguage()` の `navigator.language` だけで、これは拡張 API ですらない。
`chrome` 名前空間は `src/lib/config.ts` と `src/lib/function-store/chrome-storage.ts` に閉じている現状を維持する。

## Testing Strategy

### Catalog Tests

- `messages.ja.ts` が `typeof en` に適合することは `tsc --noEmit` が保証する。実行時のテストは書かない。
- カタログの構造を走査し、英語と日本語でキー集合と値の型 (文字列か関数か) が一致することを検証する。型で防げない値の入れ違いを検出する。

### Unit Tests

- `detectLanguage()` が `navigator.language` の値に対して期待する言語を返すこと。`ja`、`ja-JP`、`en`、`en-US`、未知の値を対象とする。
- `Config` の `language` が未設定、不正値、未知の値のいずれでも `auto` へ落ちること。既存の `config.test.ts` に追加する。

`messageForError()` の多言語テストはエラーの構造化 (後続) とあわせて書く。

### Component Tests

- `I18nProvider` に `ja` を与えたとき、popup と options が日本語で描画されること。文言ごとに検証はせず、代表的なエントリをカタログ経由で参照する (`docs/wordings.md`, "Tests")。
- Provider の外側で `useT()` が英語カタログを返すこと。
- Settings の言語セレクタが `ConfigStore.update` を呼び、`subscribe` 経由で表示が切り替わること。
- 初回描画が `detectLanguage()` の結果で行われ、`ConfigStore.read()` の解決後に明示設定の言語へ差し替わること。

既存のテストは英語で描画されることを前提とするため、Provider の既定値を英語とすることで影響を受けない。

## Migration

既存ユーザーの `cocopy:config` には `language` が存在しない。
`v.fallback` により `auto` として読まれ、ブラウザ言語に追従する。
日本語環境のユーザーは更新後に日本語表示となる。

段階的に進める。各段階は独立して動作し、途中で停止しても壊れない。

1. 基盤: `Config.language`、カタログ、`detect.ts`、`I18nProvider`、`useT()`、Settings の言語セレクタ。
2. popup: 約 6 件。最小の面積で仕組みを検証し、起動性能への影響を確認する。
3. options: 残りの UI リテラル。`Hints.tsx` の文の分割と `LegacyBackupBanner` (文言の削減・統合を含む) を対象とし、`LegacyBackup.tsx` のページ本体は対象外。
4. 整理: `src/sandbox.html` の `lang="ja"` を削除する。不可視の iframe で表示テキストを持たないため実害はないが、実態と合っていない。

本設計の範囲外として、エラーの構造化 (`src/lib/function-store/` と `src/lib/eval.ts` のエラーへ `code` と値を持たせ、`messageForError()` と `Error.tsx` で文言を決める) を後続の変更で行う (Error Messages 参照)。

## Alternatives Considered

### `i18n.getMessage()` と `_locales/`

WebExtensions 標準の仕組みであり、Chrome・Firefox・Safari のいずれも持つ。採用しない。

`getMessage()` はロケール引数を持たず、表示言語はロード時にブラウザ UI 言語で確定する。
拡張から変更する API がないため、言語を選択できるという要件を満たさない。

`_locales/` のデータを `fetch()` で直接読み `getMessage()` を迂回する方法はある。
しかしこれは翻訳の取得を非同期にし、popup の起動に処理を追加する。
`messages.json` は文字列しか持てず型検査も効かないため、迂回して得られるのは言語の切り替えだけで、他の制約は残る。

クロスブラウザでは制約が増える。Firefox と Safari の既定は MV2 であり、`_locales/` を manifest の分岐管理へ持ち込むことになる。
Safari は `_locales/` の扱いが Chrome と一致しない事例が知られており、変換後の動作確認が別途必要になる。

manifest の `name` と `description` に限れば `getMessage()` の制約は問題にならない。
それでも採用しない。対象は 2 言語で数十文字であり、ストア掲載情報は各ストアの管理画面がロケール別の入力に対応している。
`buildManifest()` (`scripts/vite-manifest-plugin.ts`) へ分岐を増やす利点がない。

### Lingui

`@lingui/core` と `@lingui/react` を合わせて gzip 約 3.8 KB、実測で最も小さい。採用しない。

`Trans` マクロは文中の JSX 要素を `<0>` `<1>` の添字タグへ変換し、1 文を 1 エントリとして保つ。
訳者がタグの位置を自由に動かせるため、文中に要素が埋め込まれた文言に対しては最良の解である。

しかしそれを必要とする文言がない。
該当する 10 件はいずれも埋め込まれた要素が翻訳対象ではなく、文の分割で解決する (Nested Elements 参照)。

導入費用は小さくない。マクロの展開に Babel または SWC が必要となるが、Vite 8 は Rolldown を使い、いずれも既定では持たない。
現在このリポジトリは Babel も SWC も持たないため、マクロの展開だけのためにトランスパイラを追加することになる。
加えて `lingui extract` と `lingui compile` の 2 ステップが増え、カタログの再生成漏れという失敗経路が生まれる。
oxc 向けのプラグインは提案段階であり、oxlint と oxfmt を使う本リポジトリとは特に噛み合わない。

3 言語目以降を追加する場合、または外部の翻訳者へ PO を渡す運用へ移る場合は、この判断を見直す。

### i18next / react-i18next

react-i18next が gzip 約 10 KB、i18next 単体が約 13.5 KB。採用しない。

実行時にキーを解決するため型検査が効かず、キーの誤りと訳の欠落を `tsc --noEmit` で検出できない。
ICU MessageFormat による複数形と書式の表現力を持つが、複数形の対象が 1 件しかない本リポジトリでは活きない。
Lingui より大きく、型安全性で劣る。

### typesafe-i18n

gzip 約 1.3 KB、依存 0 で、型安全性を持つ。採用しない。

文字列ベースであり、文中に要素が埋め込まれた文言への機構を持たない。
本リポジトリではその機構が不要なため欠点にはならないが、それは同時に、自前のカタログに対する利点もほぼないことを意味する。
加えて更新が停滞しており、新規に依存を追加する理由がない。

### キー文字列による参照

`t('settings.title')` の形式を採らない理由は Distribution に述べたとおりである。
オブジェクトを返せば補完が効き、存在しないキーが型エラーになる。
文字列キーは実行時まで誤りが残り、リテラル型を使って型付けしても、ネストの表現と補完の質でオブジェクト参照に劣る。
